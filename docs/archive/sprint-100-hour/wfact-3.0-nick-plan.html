The 100-Hour Build

What this sprint is, plainly: 100 hours is enough to prove the new architecture works end to end on one real slice of the business, not to rebuild the entire factory. You'll get a working loop you can see and judge, backed by real numbers, not a finished product. What's deliberately left for the next sprint is listed at the bottom of this page, no surprises.

The 7 phases

Phase 1 Foundation & Access Days 1–2 · 8 hrs

Get every account, credential, and open decision unblocked before any building starts, and set up the new repository with its automated safety checks running from day one.

Deliverable

A working repository with checks running automatically, and every access item either confirmed or actively tracked.

Nothing else in these 20 days can start cleanly without this.
Phase 2 State Layer & Second Brain v1 Days 3–5 · 16 hrs

Build the database that holds every client, project, and task, correctly separated by entity, and stand up a first working version of the "second brain," the shared memory every AI agent reads before doing anything.

Deliverable

A tested database schema, plus a readable memory file describing the business, its rules, and its two entities.

Every later phase now has a real place to store and retrieve information, instead of an agent guessing.
Phase 3 Hermes Controller Core Days 6–8 · 14 hrs

Stand up Hermes, the manager that decides which AI does what, and connect it to the memory and database from Phase 2, with one model wired in as the first working path.

Deliverable

Hermes answers a real question about the business, in plain language, using real data, not a canned response.

Proves the "brain" of the system works before adding anything on top of it.
Phase 4 Model Routing & Front-End Loop v1 Days 9–12 · 22 hrs

The centerpiece of the sprint: wire up the actual website-building loop, Motion Sites and 21st.dev generating a real page for one real project, checked by a second AI before anyone sees it.

Deliverable

One real front-end page, built end to end through the new stack, for a real (even low-stakes) project.

Direct, measured evidence on whether the new front-end approach actually beats 2.0's defect rate, not a guess.
Phase 5 Verification Loop Days 13–15 · 14 hrs

A small, working version of the "never trust done, only verified" discipline from 2.0: a handful of automated checks, plus a second AI reviewing the first AI's work.

Deliverable

A working check-and-fix loop that catches a deliberately broken test case before a human ever sees it.

Proves the exact discipline that was missing in 2.0 holds in 3.0, even in miniature.
Phase 6 Cockpit MVP Days 16–18 · 16 hrs

The smallest useful version of the control room: one screen showing what's running, what's waiting on you, and what's already been checked.

Deliverable

A live dashboard showing the Phase 4 and 5 loop's real status.

You get visibility into the system without needing to ask what's happening right now.
Phase 7 Proof Run & Handoff Days 19–20 · 10 hrs

Run the whole thing once, start to finish, on the real pilot project, and document honestly what worked, what didn't, and what the next sprint needs to cover.

Deliverable

A short, honest results report, plus a clear, evidence-based list of what's proven versus what's still ahead.

A real basis for deciding what comes next, backed by a working system, not a slide deck.

What you'll have after Day 20

  • One real page or project built end to end through the new architecture: controller, memory, model routing, verification, and cockpit visibility, all working together.
  • A real, logged correction-round count for that build, measured against DreamSign's 40+ from 2.0.
  • A working, if minimal, version of every core system: second brain, controller, front-end loop, verification loop, and cockpit.
  • Honest, tested data on whether Kimi K3 is actually worth using over the MCP combination alone.
  • A clear, evidence-based scope for the next sprint, not a guess.

What's deliberately not in this sprint

This is a scope choice, not a shortfall. These are real, planned parts of WFACT 3.0 that simply need more than 100 hours, and are sequenced for the sprint after this one:
  • The full 11-stage client pipeline (this sprint proves the front-end build and verification stages only)
  • The full cockpit room set (Money, SEO, Content, Calendar, and the rest)
  • The complete 78-check security and feature registry (a focused 5–8 check set is proven instead)
  • Cognee or any full knowledge-graph second brain (a flat-file version proves the concept first)
  • Local/open-source model evaluation (its own separate, parallel track, unaffected by this sprint)
  • Running multiple clients concurrently
  • Back-end, content, and SEO agent loops (only the front-end and verification loop are proven this sprint)
