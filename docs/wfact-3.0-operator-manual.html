Build Operator's Manual

Your day-by-day field guide for the 100-hour sprint

Every phase, what it actually requires from you and from Nick, what to do when something doesn't go to plan, and the exit check that proves a phase is actually done, not just attempted. Use this daily, tick things off as you go, don't skip the exit checks.

How to use this page: work top to bottom, phase by phase. Each phase has a checklist, a two-column box showing exactly what's blocked on Nick versus what's entirely on you, a list of realistic edge cases with a pre-decided fallback (don't improvise live, use the fallback), and an exit check, the thing that has to be true before you move on. If a phase overruns its hour budget, cut scope inside that phase first. Never borrow hours from a later phase.

The 7 phases

01 Foundation & Access Days 1–2 · 8 hrs▶

Objective

Unblock every account, credential, and open decision before writing any code, and get the new repo running with checks from day one.

Checklist

  • Confirm GitHub access: existing 2.0 repo + new 3.0 repo created
  • Confirm Supabase project access
  • Confirm Vercel + Hostinger account access
  • Pull the 3 SOPs + Ops Manual from Nick's Drive
  • Get Motion Sites MCP + 21st.dev premium credentials
  • Get Higgsfield MCP credentials
  • Confirm Claude/Anthropic API billing setup
  • Confirm which 2 entities
  • Set up repo skeleton, secrets manager, base CI

Requirements

From Nick
  • Every access item above
  • Entity decision (which 2)
  • Budget ceiling sign-off for the sprint's API spend
From you
  • Repo scaffold + branch protection
  • CI pipeline skeleton
  • Secrets manager wired, nothing in plaintext

Edge cases & fallbacks

  • Access delayed Don't sit idle. Scaffold the repo and CI with placeholder credentials, swap in real ones the moment they land. Keep a visible "blocked on Nick" list rather than quietly waiting.
  • GitHub org/seat constraints Ask for collaborator access on the existing account instead of waiting on a new org to be provisioned.
  • Entity decision still pending Use placeholder names (Entity A / Entity B) in the schema now, don't block Phase 2 on it, rename later, it's a one-line change.
Exit check

A commit reaches a deployed preview through CI with zero manual steps, and every access item is either confirmed or has a tracked workaround in place.

02 State Layer & Second Brain v1 Days 3–5 · 16 hrs▶

Objective

A tested database for clients, projects, and tasks, plus a first working, readable memory layer.

Checklist

  • Design Supabase schema: clients, projects, tasks, 2 entities
  • Write RLS policies
  • Run an isolation/RLS attack test, adapted from 2.0's script
  • Draft context.md: business rules, entities, pricing bands
  • Set up the per-client memory file template

Requirements

From Nick
  • 30–60 min session to supply real business rules and pricing bands for context.md
  • Confirm entity names once decided
From you
  • Schema, RLS policies, attack test
  • context.md and per-client memory file structure

Edge cases & fallbacks

  • 2.0's schema is messier than expected Don't migrate old data or structure. Build fresh, informed by 2.0's lessons, not its code.
  • Full Cognee graph setup won't fit the time box That's expected, it's not in this sprint's scope. Flat files (context.md + per-client markdown) are the deliberate v1, not a compromise you need to apologize for.
  • Nick's session gets delayed Draft context.md with placeholder rules pulled from the Factory Book and Blueprint, mark them clearly as drafts, swap in Nick's real answers when the session happens.
Exit check

A test query ("what stage is client X in") returns a correct answer from the memory files, and the RLS attack test fails to cross entity boundaries.

03 Hermes Controller Core Days 6–8 · 14 hrs▶

Objective

Hermes (or a working stand-in) wired to memory and state, answering real questions in plain language.

Checklist

  • Self-host Hermes Agent
  • Wire to memory (context.md + per-client files) and Supabase
  • Configure Claude as the first model behind it
  • Build the plain-language tone filter
  • Smoke test with a real status question

Requirements

From Nick
  • None blocking this phase
From you
  • Hermes install and config
  • Tone filter
  • The smoke test itself

Edge cases & fallbacks

  • Hermes self-hosting eats more time than budgeted Fallback: build "Hermes-lite," a thin script that reads memory, calls Claude, and applies the tone filter. Use it for this sprint, swap in real Hermes once there's runway. Tell Nick if you do this, don't substitute silently.
  • Hermes's native MCP support is rough Wire the needed tools directly through Claude's own MCP support for now, migrate to Hermes-native once it's stable.
Exit check

Hermes (or its stand-in) answers "what's the status of X" correctly and in plain language, sourced from real memory and state, not a canned response.

04 Model Routing & Front-End Loop v1 Days 9–12 · 22 hrs▶

Objective

The centerpiece: one real page built end to end through Motion Sites + 21st.dev, checked by a second AI before anyone sees it. The biggest hour allocation in the sprint on purpose, this is what 2.0 struggled with most.

Checklist

  • Wire Motion Sites MCP
  • Wire 21st.dev MCP
  • Configure the front-end agent (Kimi K3 as candidate executor)
  • Get one real pilot brief from Nick
  • Run the loop: generate → self-review → fix → done
  • Log every correction round, this number is the whole point

Requirements

From Nick
  • One real, even low-stakes, project brief to use as the pilot
  • Same-day answer if a direction question comes up mid-build
From you
  • The loop itself, agent config, correction tracking

Edge cases & fallbacks

  • 21st.dev's React/Tailwind lean doesn't match how sites actually ship Hand-pick 2–3 templates manually for this proof instead of full dynamic selection. Note it as a fix-later item, don't let it block the phase.
  • Kimi K3 API access is delayed Use Claude for front-end generation this sprint, swap Kimi K3 in once access lands. This is also genuinely useful data on whether Kimi K3 is even needed, log it as such.
  • First-pass output is rough Expected. The proof is whether the loop catches and fixes it, not first-pass perfection.
  • No pilot brief from Nick by day 9 Use a placeholder brief from an existing 2.0 case (e.g., re-run a DreamSign-style page) so the phase isn't blocked, swap to Nick's real brief the moment it arrives.
Exit check

One real page live, plus an honest correction-round count logged and compared against DreamSign's 40+.

05 Verification Loop Days 13–15 · 14 hrs▶

Objective

A working, if trimmed, version of "never trust done, only verified."

Checklist

  • Pick 5–8 highest-value checks from 2.0's 78 (no console errors, responsive check, secrets scan, image optimization, isolation check)
  • Wire an independent evaluator step, a different model than the builder
  • Test with a deliberately broken build, confirm it's caught

Requirements

From Nick
  • None blocking this phase
From you
  • Check scripts, evaluator wiring, the test case itself

Edge cases & fallbacks

  • No time for a truly separate model as evaluator Use a strict written rubric plus a separate Claude session as a stand-in, flagged clearly as temporary until Kimi K3 or GPT-5.6 access allows a real cross-model check.
  • Tempted to build all 78 checks Don't. 5–8 well-chosen checks proving the loop works is the actual goal this sprint, completeness is next sprint's job.
Exit check

A deliberately broken test build gets caught and returned before being marked done.

06 Cockpit MVP Days 16–18 · 16 hrs▶

Objective

The smallest useful control room: one screen, live status, no logs required.

Checklist

  • Build a minimal dashboard: status, approvals, recent runs
  • Connect it to Supabase for live data
  • Get Nick to actually look at it before day 20

Requirements

From Nick
  • 10–15 minutes to look at the MVP and give real reaction
From you
  • The dashboard build itself

Edge cases & fallbacks

  • A full React PWA doesn't fit the time box A single, minimally styled page reading straight from Supabase is enough for this sprint. The full room set from the Blueprint is explicit post-sprint work, not a gap in this one.
  • Even that's tight A live Notion or Airtable view synced from Supabase is an acceptable stand-in for the proof. Not a permanent choice, just enough to hit the exit check.
Exit check

Nick can open one link and understand what's happening without asking a question first.

07 Proof Run & Handoff Days 19–20 · 10 hrs▶

Objective

Run it once for real, document it honestly, and set the next sprint's scope with actual evidence.

Checklist

  • Run the full mini-pipeline once, end to end, on the pilot project
  • Log real numbers: correction rounds, time taken, what the verification loop caught
  • Write the honest results report: what's proven, what's not
  • Present to Nick, agree on the next sprint's scope

Requirements

From Nick
  • Attend the review
  • Decide what happens next
From you
  • Run it, document it honestly, resist inflating the result

Edge cases & fallbacks

  • The full loop isn't 100% working by day 19 Don't fake it. Present exactly what's proven and what's still broken, with a concrete plan attached. That's more valuable to Nick than a staged demo, and it's the same standard this whole document holds everything else to.
Exit check

A documented, real run with real numbers that Nick has actually seen and responded to.
